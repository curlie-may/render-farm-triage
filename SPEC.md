# SPEC.md

Project specification for the render farm triage agent.

**Companion documents.** `FAULTS.md` is the authoritative specification for the
dataset and the fault design; this document does not restate it and defers to it on
anything about the data. `verify.md` is generated by `verify.py` and holds the
measured evidence that the dataset is sound.

**Status.** Domain, track, stack, fault design, and the tool layer are closed and
built. The six tools are deployed and verified against production at
`https://render-farm-triage.vercel.app`. Sections marked **[UNCONFIRMED]** are
proposals that have not been decided yet and are the open questions in this document.

---

## 1. What this is

An agent that diagnoses overnight render farm batch failures across all jobs on a
shared farm, works out which failures share a root cause and which are unrelated
noise, and hands back an ordered re-queue plan for a human to approve step by step.

**The problem it solves.** Existing schedulers (Deadline, OpenCue) organize failures
per-job and per-node. Neither performs cross-job dimensional analysis. When one bad
node group is failing tasks from four different shots, each artist sees only their own
failures and concludes their scene is broken. The pattern is invisible from inside any
single job's view, and that is precisely where simultaneous root causes hide.

**Who it's for.** Small studios with no dedicated pipeline staff, where whoever checks
the farm in the morning does the triage before they can get back to their own work.

**What it is not.** Not a scheduler, not a monitoring dashboard, not a renderer. It
reads a night's task history and reasons about it.

## 4. Data layer

Three ClickHouse tables, DDL in `db/schema.sql`:

- **`render_task_attempts`** — one row per task attempt, 9,996 rows. The dataset.
  Success rows carry `peak_mem_gb` so the agent has a control group.
- **`farm_nodes`** — 100 rows, static fleet inventory. Carries current fleet
  `renderer_version`, which is deliberately distinct from the per-attempt version:
  the agent needs current state to reason about whether a rollback has happened.
- **`past_incidents`** — 14 rows of prior incident history, hand-authored prose.

Generated by `generate.py` from a committed RNG seed (`20260909`), written as Parquet,
verified by `verify.py`, then loaded by `load.py`. The generator never writes to
ClickHouse. `verify.py` was written without access to `generate.py` and identifies the
fault groups from observable columns, so it checks the artifact rather than agreeing
with the code that produced it. It reports 11 of 11 checks passing, identically
against the Parquet and against the loaded table.

Ground truth is knowable because the faults were injected deliberately. This is what
lets the submission claim the agent recovered all three faults and correctly declined
to explain the residual — a claim almost no hackathon entry can make.

## 5. Tools

Six tools. Each is a parameterized SQL query against ClickHouse, exposed to the agent
through Agent Builder. **The tool layer is the real deliverable.** If orchestration
goes sideways late, six working tools over a sound dataset is still a demo — drive it
manually and narrate the reasoning. That is why this layer gets built before the
agent.

Signatures below are implemented and tested against known answers from FAULTS.md.
All six are Next.js API routes under `app/api/tools/`, backed by `lib/clickhouse.ts`
and `lib/stats.ts`, with an `openapi.yaml` for Agent Builder.

**Every response has the same shape:** a `summary` string generated server-side by
fixed logic for the model to quote, and a `data` object with the raw numbers. No tool
returns a statistic without an interpretation attached. Errors return HTTP 200 with an
`error` field.

### `get_failure_summary`
Entry point. Returns total attempts, total failure rows, unique failed tasks after
retry dedupe, and a breakdown by `error_class`.
Params: none (scoped to the batch window).

### `classify_error_samples`
Returns representative `error_text` samples per `error_class`, with counts, so the
agent can infer mechanism rather than grouping on the class label alone.
Params: `error_class`, `limit`.

### `test_dimension_concentration`
The core analytical tool. For a given dimension, compares each value's share of a
failure subset against its share of all attempts, and returns counts, shares, and a
significance measure.
Params: `dimension` (one of `node_group`, `node_id`, `shot_id`, `job_id`,
`renderer_version`, `submitted_by`, `uses_hair_shader`, `error_class`, `time_bucket`),
optional `error_class` filter, optional time window.

Returns both, per value: `observed_failures`, `total_failures`, `observed_share`,
`expected_share` (the value's share of all attempts — the base rate), `attempts`,
`p_value`, `p_corrected` (Bonferroni across the values tested in that dimension), and
a `verdict` string from a fixed threshold — `strong concentration` below 0.001,
`concentration above base rate` below 0.05, `no concentration above base rate`
otherwise. A dimension-level verdict reads `no value in this dimension concentrates
above base rate` when nothing clears 0.05; that sentence is what the agent needs for
the residual, which is graded.

When `dimension = time_bucket`, the response also carries a `contiguous_window`
object: `start`, `end`, `span_minutes`, `failures_in_span`, `total_failures`,
`attempts_in_span`, and `share_of_span`. This exists because fixed 10-minute buckets
cut at :00, :10, :20, and Fault C's stall runs 02:08:24 to 02:18:36 — straddling an
edge, so the bucket breakdown splits it 13/1 and understates a contiguous event. The
window statement is boundary-independent: "14 of 14 failures fall within an 11-minute
span, against 191 attempts in that span." That is the sentence that makes Fault C
identifiable as a transient, and without it a deliberately easy fault is artificially
hard for a reason unrelated to the fault. The bucket breakdown and its p-values are
unchanged — the window is added alongside, not instead.

Note that `share_of_span` is 7.33%: 14 of 191 attempts in the stall window failed, not
all of them. The agent can conclude that failures cluster hard in the window and
nothing else explains them; it cannot conclude that everything failed during it. That
is the correct level of certainty for a brief NFS stall.

The two-sided binomial uses the exact PMF-comparison method in log space, validated
against scipy at 1.0002, 0.9999, and 0.9437 on the three known values in `verify.md`.
An earlier tail-doubling implementation inflated every significant finding by exactly
2× and was replaced.

### `check_success_elsewhere`
The reverse test, and the thing that separates Fault A from Fault B. Given a suspected
culprit value, returns where tasks matching it succeeded and where they failed, broken
down along a chosen axis.
Params: `dimension`, `value`, `split_by` (one of `node_group`, `renderer_version`,
`uses_hair_shader`, `before_after_2300`).

Returns attempts, successes, failures, and failure rate per bucket, plus a plain
summary sentence chosen by a fixed 5× ratio threshold with a 5% absolute floor. This
tool runs **no** hypothesis test and returns no p-value — it answers a descriptive
question, and concentration testing stays in `test_dimension_concentration`. The
`split_by` parameter matters: `shot_012` split by `node_group` shows group B at 45.7%
against 0.6% and 1.4%, but split by `renderer_version` shows 7.3.1 at 50.9% against
0.9%, which is the real axis.

### `query_similar_past_incidents`
Retrieval over `past_incidents`. Returns prior incidents matching an error class
and/or a dimensional signature, with their root cause and remediation.
Params: `error_class`, optional `dimension_signature`.

### `get_farm_capacity`
Returns node counts by group, memory per node, current renderer version per group,
and available node-hours in a given window. Feeds the capacity constraint in the
plan.
Params: `window_hours`.

## 6. Agent behavior

### Required reasoning discipline

The system prompt must enforce these. Expect most prompt-iteration time here.

1. **Dedupe retries before counting.** 396 failure rows are 294 unique tasks. Any
   count presented to the human is a task count, not a row count.
2. **Never attribute to a dimension without checking the control group.** A dimension
   lighting up is a hypothesis, not a finding. `check_success_elsewhere` is what turns
   it into one.
3. **Consider time and dimension jointly.** Group B ran clean for the first hour.
   "Group B is bad" is false for most of the night.
4. **Use the retry signature.** Second-attempt failure rate discriminates node-located
   (31.6%) from content-located (100%) from transient (0%) faults more cheaply than any
   other single test.
5. **State when no pattern is found.** Do not invent a story for the residual. This is
   graded.
6. **Sequence the plan by dependency, not by volume.** The rollback precedes the
   re-queue because a re-queue without it sends ~30% of tasks back onto bad nodes.

### Required output

Per `FAULTS.md` § "What the agent must produce": a root cause in words per fault, a
concrete remediation per fault, the order C → A → B → residual with reasoning, and
correct restraint on the residual.

## 7. Interface

The mockup is the spec. Build it, don't redesign it.

- **Editable delivery target and farm capacity inputs.** The human sets the
  constraint; the plan responds to it.
- **Ordered remediation steps**, each showing the fault, the affected task count, the
  action, the reason, and the dependency that fixes its position in the order.
- **A capacity shortfall that forces a real prioritization decision.** Required
  node-hours exceed available node-hours in the window, so the human has to choose
  what slips. **[UNCONFIRMED]** — the mockup used 3.5h needed against 2.9h available;
  those figures predate the rescale to ~10,000 attempts and must be recomputed from
  the actual dataset (294 tasks at ~4.8 min each is ~23.5 node-hours of work). Pick
  the window so the shortfall is real but not absurd.
- **Per-step Accept / Modify / Reject controls.** The human approves each step. The
  agent never executes.
- **A residual block that declines to explain.** Displayed as unexplained, re-queue
  at lowest priority, with the concentration tests that came back empty shown as
  evidence. This block is a feature, not an omission.

### Out of scope

No auth. No multi-user. No settings page. No live farm connection. No writes back to
any scheduler. UI is the easiest thing to over-invest in because progress feels
visible — if the interface is being polished before the agent works, that is
avoidance.

## 10. Open questions

- Capacity shortfall figures in § 7 — recompute against the real dataset before the
  interface is built. **[UNCONFIRMED]**

### Settled

- Tool signatures — implemented and tested; § 5 records what was built.
- `test_dimension_concentration` returns both a p-value and a verdict string, the
  verdict derived server-side from a fixed threshold. The p-value keeps the claim
  honest and auditable; the verdict gives the model something unambiguous to act on,
  which matters most for the residual, where restraint is graded.

### Worth knowing

- Two figures describe group B's concentration and they are not interchangeable.
  **278 of 334 OOM rows (83.2%) at p = 2.31e-90** is the before-the-split test — what
  the agent sees when it first groups by error class. **250 of 250 at p = 1.96e-131**
  is the after-the-split test and is circular as evidence *for* the split. Quote the
  334-row figure publicly.
